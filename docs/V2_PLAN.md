# ふじさわレンズ V2 改善計画

調査日：2026-10-28。対象：公開中の https://seg1gpt0jpn.github.io/Fujisawa-renzu/（`main` = d156bfe）とリポジトリ。
計測：Playwright/Chromium、スマートフォン幅 390×844px。

## 1. 現状の問題点と根拠

## 2. 優先順位

1. **誤案内の防止（P4, P5, P3）**：災害種別ごとの照合と除外、津波避難ビル・高潮の案内、「指定」と「開設」の区別
2. **災害時の操作順（P1, P2, P6）**：ホームから災害種別を1タップで選んで検索画面へ。検索画面は「種別→探し方→結果」を1画面目に収める。結果は簡潔にし、詳しい情報は折りたたむ
3. **混雑（P7）**：公式の開設・混雑情報への導線を最優先にし、未設定のAPIは小さく「準備中」とだけ表示する。本番前の確認項目を文書化する
4. **環境ページ（P8, P9）**：250m格子の地図（年の切替・差分）、大気の推移グラフ、水質の比較表。各データに「データの見方」を常に表示する
5. **日頃の備え**：端末内にだけ保存する防災チェックリスト

## 3. 修正対象ファイルと実装内容

### 第1段階
- `scripts/lib/shelters-core.mjs`, `scripts/fetch-shelters.mjs`：照合を**災害種別ごと**にする（`hazardChecks`）。
  - 市の一覧に該当する列がある災害種別で「国土地理院：指定あり／市：指定なし」の場合は、その種別の検索対象から外す（`excludedHazards`）。
  - 「市：指定あり／国土地理院：なし」の場合は、推奨には使わず「公式一覧で確認が必要」として別枠に名前だけ出す（`cityOnlyHazards`）。距離順の推奨には混ぜない。
- `site/assets/js/geo.js`：`filterFacilities` で `excludedHazards` を考慮する。
- `site/shelters.html`, `site/assets/js/shelters.js`：画面を再構成する。
  - 種別を大きなボタンで選ぶ → 「現在地から」「地区・名前で」の2択 → 結果の順に並べる。`?hazard=` で種別を受け取る。
  - 注意は1行の要約にまとめ、詳細は折りたたむ。
  - 結果カードは簡潔にし、施設名・直線距離・住所・「地図」「経路」だけを常に表示する。
  - 結果の先頭に「これは指定施設の一覧で、開設しているかは公式の開設状況で確認」と公式導線を置く。
  - 津波・高潮の場合は、結果より前に津波避難ビル・高潮指定先の案内を出す。
- `site/index.html`, `site/assets/js/home.js`：3つの入口（災害時／環境／日頃の備え）にする。災害時は種別ボタンから直接検索画面へ移る。データ更新状況は出典ページへ移す。
- `site/crowding.html`, `site/assets/js/crowding.js`：公式の開設・混雑情報を大きなボタンにする。API未設定時は利用者報告の画面を出さず、1行の「準備中」だけにする。
- `docs/CROWDING_API_PRODUCTION_CHECKLIST.md`：本番運用前の確認項目（プライバシー、保存期間、投稿制限、虚偽報告、運用ログ、停止手順）。

### 第2段階
- `scripts/env/landcover_grid.py`（新規）：JIS 地域メッシュの 1/4 細分区画（約250m）ごとに、市域内画素の分類割合を集計する（2020/2022/2024）。
  - 分類は5区分にまとめる：建物・道路等／農地（水田・畑・温室）／樹林・竹林・草地／水域・湿地・干潟／その他。
  - 境界は N03 を簡略化した市の輪郭のみを同梱する（CC BY 4.0）。
  - 出力 `site/data/environment/landcover-grid.json`（詳細データ。地図を開いたときだけ読み込む）。
- `site/environment.html`、`site/assets/js/env-*.js`：土地被覆の格子地図（SVG、年・区分・差分の切替、区画をタップすると内訳）、大気の推移グラフ（局・項目・期間の選択、一般局と自排局の区別、欠測は線を途切れさせる）、水質の比較表（年度・回・海水浴場）。
- 各データ共通の「データの見方」：何を／いつ／どの範囲／判断できないこと／出典と利用条件。

### 第3段階
- `site/prepare.html`、`site/assets/js/prepare.js`、`site/data/checklist.json`：公式資料に基づく項目、災害種別ごとの追加項目、進捗は `localStorage` のみ（送信なし）。

## 4. データ精度・利用条件の課題

- **避難先**：国土地理院データには施設ごとの更新日がない。照合元の藤沢市ページは「無断転載禁止」のため、照合結果（指定の有無の一致）以外は配信しない。「市のみ指定あり」の施設は名前と市の一覧へのリンクだけを示し、推奨しない。
- **開設状況**：当サイトでは取得できない（市とVACANの公式マップのみ）。そのため、当サイトで「開設中」を表示することは一切しない。
- **土地被覆の格子**：
  - 1区画は約250m×250mで約530画素。分類誤りは区画内で一部平均化されるが、年ごとの差には分類のゆらぎ（2022年版は作り方も一部異なる）が含まれる。
  - 差分表示では、±5ポイント未満を「差が小さい（誤差の範囲の可能性）」として色分けしない。原因の断定はしない。
  - 地域メッシュはコード体系（JIS X 0410）で、利用条件の制約はない。JAXA の利用条件（出所表示・加工の明示、商用利用は事前連絡）と N03（CC BY 4.0）に従う。
  - 配布サイズの目安は、gzip後30KB程度、閲覧時のみ取得。
- **大気**：年平均値は環境基準の判定指標ではない。自排局と一般局は同列に比較しない。原因（交通量・気象・規制など）はデータから特定できない。
- **水質**：年2回・各2日の採水に基づく判定で、測定値は公表資料にない。県サイトに明示的なオープンライセンスはない（V1と同様、事実のみ出典つきで抜粋）。
- **チェックリスト**：数量など具体的な値は、公式資料に記載がある場合のみ表示し、出典を明記する。

## 5. 実装後のテスト方法

- 単体：災害種別ごとの照合・除外（両方向の不一致、該当列がない場合）、`filterFacilities` の除外、チェックリストの保存処理、格子データの検証（割合の合計・null の扱い）、グラフで欠測を0にしないこと。
- ブラウザ：
  - ホームから災害種別を1タップで選び、検索画面で種別が選ばれていること。
  - 種別ボタンと「現在地から探す」が1画面目に収まること。
  - 結果の先頭に開設状況の注意と公式導線があること。津波を選ぶと結果より前に津波避難ビルの案内が出ること。
  - 除外された種別に施設が出ないこと。混雑APIが未設定のとき報告画面が出ないこと。
  - 環境ページで地図を開くまで格子データを読み込まないこと。局・項目の切替でグラフが更新されること。
  - チェックリストの進捗が再読み込み後も残り、通信が発生しないこと。
  - 既存の全テスト（モバイル幅・外部通信なし・オフライン・GPS拒否など）。
- 通信量（`npm run measure`）、axe-core による自動アクセシビリティ検査、リンク確認。
