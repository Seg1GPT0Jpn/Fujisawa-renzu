# 混雑共有API 本番運用前チェックリスト

混雑共有API（`worker/`）を本番公開する前に、運用者が確認する項目です。すべて確認できるまで、`site/config.js` の `crowdingApiBase` は空のままにしてください。空のあいだ、画面には「準備中のため利用できません」と1行だけ表示され、報告の送信・表示は行いません。

確認した日付と確認者を各項目に記入し、このファイルをコミットしてから公開してください。

## A. プライバシー

- [ ] Cloudflare Workers の Observability（ログ）を無効にしている（`wrangler.toml` の `[observability] enabled = false`）。有効にする場合は保存期間と内容を `privacy.html` に書く。
- [ ] Cloudflare のダッシュボードで、Workers Logs・Logpush・Tail などを常時有効にしていない。
- [ ] Cloudflare 自体がIPアドレス等をどう扱うか、その時点の公式ドキュメント（プライバシーポリシー・データ処理）を読み、`privacy.html` の「サーバー基盤」の説明と食い違いがない。
- [ ] `RATE_LIMIT_SECRET` は十分に長いランダム値で、`wrangler secret` だけに保存している（リポジトリ・チャット・メールに書いていない）。
- [ ] D1 に保存されるのが `reports`（施設ID・区分・時刻）と `rate_events`（ハッシュ化キー・施設ID・時刻）だけであることを、本番 D1 で `SELECT` して確認した。
- [ ] リクエスト本文に余計な項目（位置情報など）があると拒否されることを本番で確認した（`unexpected_fields`）。

## B. 保存期間

- [ ] `RETENTION_HOURS`（初期24時間）と `rate_events` の1時間保持が、`privacy.html` の記載と一致している。
- [ ] Cron（`*/30 * * * *`）が動いて古い行が削除されることを、本番で時刻をおいて確認した。
- [ ] D1 のバックアップ（Time Travel）の保持期間を確認し、削除後も一定期間復元できる場合はその旨を `privacy.html` に書いた。

## C. 投稿制限

- [ ] `ALLOWED_ORIGINS` が公開サイトのオリジンだけになっている（例：`https://seg1gpt0jpn.github.io`）。
- [ ] 同じ回線から同じ施設への10分以内の再投稿が拒否される（429）ことを確認した。
- [ ] 1時間あたりの上限（初期10件）と、施設ごとの1分間上限（初期30件）が働くことを確認した。
- [ ] 避難所の Wi-Fi のように多くの人が同じ回線を使う場合、正当な報告まで制限されうることを理解し、上限値を決めた。
- [ ] Cloudflare の無料枠（リクエスト数・D1 の読み書き量）を超えたときの挙動（エラーになる、課金される等）を確認した。

## D. 虚偽報告・いたずらへの対策

- [ ] 画面に「利用者からの報告で、公式情報ではない」「誤った報告が含まれうる」と表示されることを確認した。
- [ ] 報告が3件未満、または「わからない」を除くと3件未満の場合は「情報不足」と表示され、混雑度を断定しないことを確認した。
- [ ] 区分が拮抗している場合に「ばらつきあり」と表示されることを確認した。
- [ ] 大量の虚偽報告を見つけたときの対応を決めた：
  - `crowdingApiBase` を空にして再公開する（画面は「準備中」に戻る）
  - D1 の該当行を削除する
  - 必要なら Worker を停止する（`wrangler delete` またはルートの無効化）
- [ ] 公式情報（藤沢市の開設・混雑マップ）と食い違う場合は公式情報を優先するよう、画面に案内があることを確認した。

## E. 運用

- [ ] 災害時に誰が監視し、誰が停止を判断するかを決めた。
- [ ] 施設データを更新したら `node scripts/build-worker-ids.mjs` を実行し、Worker を再デプロイする手順を確認した。
- [ ] `npm test` と `npm run test:browser` が成功した状態でデプロイした。
